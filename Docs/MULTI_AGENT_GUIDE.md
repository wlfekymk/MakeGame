# MakeGame 멀티 에이전트 개발 구조 가이드

> 무인도 생존 게임(Unity) 프로젝트를 **1인 에이전트 → 역할 분담 팀 구조**로 전환하기 위한 가이드.
> 최종 수정: 2026-08-14

---

## 1. 왜 바꾸는가

현재는 하나의 에이전트가 기획·구현·UI·아트·검증·커밋을 전부 순차로 처리한다. 프로젝트가 커지면서 생기는 문제:

| 증상 | 원인 |
|---|---|
| 컨텍스트가 금방 가득 참 | 50개+ 스크립트를 한 세션이 전부 기억해야 함 |
| UI 고치다 시스템 로직이 틀어짐 | 관심사가 섞여서 한 번에 너무 넓게 수정 |
| 컴파일 에러를 나중에 발견 | 구현자가 곧 검증자라 자기 코드를 관대하게 봄 |
| 20개 배치 1회가 너무 오래 걸림 | 병렬화 가능한 작업(UI/아트/시스템)을 직렬로 처리 |

역할을 나누면 **각 에이전트가 좁은 컨텍스트만 들고** 일하고, 겹치지 않는 작업은 **동시에** 돌릴 수 있으며, **검증자가 구현자와 분리**된다.

## 2. 전체 구조

```
                    ┌──────────────────────┐
                    │  디렉터 (메인 세션)   │  ← 사용자와 대화하는 나
                    │  20개 배치 리스트업   │
                    │  작업 분해 · 위임 · 통합 │
                    └──────────┬───────────┘
                               │
         ┌──────────┬──────────┼──────────┬────────────┐
         ▼          ▼          ▼          ▼            ▼
   ┌──────────┐ ┌────────┐ ┌────────┐ ┌─────────┐ ┌──────────┐
   │ 기획자    │ │시스템  │ │  UI    │ │테크아트 │ │  QA      │
   │designer  │ │engineer│ │engineer│ │artist   │ │reviewer  │
   └────┬─────┘ └───┬────┘ └───┬────┘ └────┬────┘ └────┬─────┘
        │           │          │           │           │
        │  스펙 →   └───── 병렬 구현 ──────┘     ← 정적검증│
        │                      │                        │
        └──────────────────────┴────────────────────────┘
                               ▼
                    ┌────────────────────┐
                    │  unity-operator    │  ← ★ 단독 전용, 항상 1개만
                    │  Unity 실기 검증    │     (마우스·키보드는 하나뿐)
                    └─────────┬──────────┘
                              ▼
                        ┌─────────────┐
                        │ 빌드/릴리스  │  ← 단독 실행 (git lock 때문)
                        │ build-master│
                        └─────────────┘
```

핵심 2가지:
- **디렉터는 코드를 직접 안 짠다.** 무엇을 할지 정하고, 누구에게 줄지 결정하고, 결과를 합친다.
- **컴퓨터(Unity)를 조작하는 에이전트는 단 하나.** 나머지는 전부 파일만 다룬다.

## 3. 역할 정의 (7개)

### 3.1 `game-designer` — 기획 / 밸런스

- **한 줄**: 요구사항을 "구현 가능한 스펙"으로 번역한다.
- **하는 일**: 기능 스펙 작성, 수치 밸런싱(허기·갈증·체력 감소율, 크래프팅 비용, 스폰 확률), 아이템/레시피 ScriptableObject 데이터 설계, 스토리·엔딩 조건 정의
- **소유 파일**: `Docs/**`, `Assets/_Project/ScriptableObjects/**/*.asset`
- **하면 안 되는 것**: `.cs` 파일 직접 수정
- **산출물 형식**: "무엇을 / 어떤 수치로 / 어느 파일에" 가 명시된 스펙. 애매한 표현 금지.

### 3.2 `systems-engineer` — 시스템 프로그래머

- **한 줄**: 게임플레이 로직의 뼈대를 만든다.
- **하는 일**: 생존 스탯, 크래프팅, 스폰, 날씨, 낮밤, 세이브/로드, 상호작용, 위험요소, 섬 생성
- **소유 파일**: `Assets/_Project/Scripts/Systems/**`, `Scripts/Player/**`, `Scripts/Utils/**`, `Scripts/Enemy/**`
- **하면 안 되는 것**: `Scripts/UI/**` 수정 (UI가 필요하면 public 프로퍼티/이벤트만 노출하고 UI 담당에게 넘김)
- **필수 규칙**: 새로 만든 모든 메쏘드에 한글 요약 주석 (프로젝트 지침)

### 3.3 `ui-engineer` — UI 프로그래머

- **한 줄**: 플레이어가 보는 화면을 만든다.
- **하는 일**: HUD, 인벤토리, 크래프팅 창, 미니맵, 메인메뉴, 설정, 게임오버, 경고 표시
- **소유 파일**: `Assets/_Project/Scripts/UI/**`, `Assets/_Project/Resources/UI/**`, `Resources/Sprites/**`
- **하면 안 되는 것**: `Scripts/Systems/**` 안의 게임 규칙 변경. 데이터가 부족하면 시스템 담당에게 "이 값을 public으로 열어달라"고 요청
- **주의**: 이 프로젝트는 UI를 코드로 생성(`UIBuilder.cs`)한다. 씬에 직접 배치하지 말 것.

### 3.4 `tech-artist` — 테크아트 / 에셋

- **한 줄**: 보이는 것(텍스처·프리팹·머티리얼·사운드)을 만든다.
- **하는 일**: 절차적 텍스처/아이콘 생성, 프리팹·머티리얼 구성, 오디오 클립 생성, `.meta` import 세팅
- **소유 파일**: `Assets/_Project/Art/**`, `Resources/Textures/**`, `Prefabs/**`, `Audio/**`, 관련 `.meta`
- **주의**: Unity에서 `.png`/`.prefab` 추가 시 **반드시 `.meta` 파일도 함께** 만들거나 Unity에서 Refresh해서 생성시킬 것. GUID 충돌은 이 프로젝트 최대 사고 원인.

### 3.5 `qa-reviewer` — QA / 코드리뷰 (읽기 위주)

- **한 줄**: 남이 짠 걸 의심한다.
- **하는 일**: 컴파일 에러 후보 탐지(참조 누락, 시그니처 불일치, 네임스페이스), 프로젝트 규칙 위반 검사(**메쏘드 주석 누락**), null 참조 위험, 밸런스 수치가 스펙과 일치하는지 대조
- **소유 파일**: 없음 (**읽기 전용**). 문제를 찾아서 "파일:줄 → 무엇이 문제 → 어떻게 고쳐라" 로 보고만 한다.
- **왜 읽기 전용인가**: 검증자가 직접 고치면 다시 검증자가 없어진다. 수정은 원래 담당 에이전트가 한다.

### 3.6 `unity-operator` — Unity 조작 (★ 단 하나만 존재)

- **한 줄**: Unity 에디터를 실제로 눌러보는 유일한 에이전트.
- **하는 일**: `Assets > Refresh`(Ctrl+R) 강제 재컴파일, Console 에러 원문 확인, 새 에셋 임포트 확인, Play 실행 후 초기화 런타임 에러 확인 및 정지, Inspector 값 육안 확인
- **소유 파일**: 없음. **조작하고 관찰만 한다.**
- **왜 하나여야 하는가**:
  - 사용자 PC의 마우스·키보드는 **물리적으로 하나**다. 두 에이전트가 동시에 클릭하면 서로 입력을 덮어써서 엉뚱한 메뉴를 누른다.
  - Unity는 상태 기계다. 한쪽이 Play를 켜는 동안 다른 쪽이 Refresh를 걸면 씬이 저장되지 않은 채 재컴파일되어 작업이 날아갈 수 있다.
  - 병렬화해서 얻는 이득이 0이다. Unity는 어차피 한 번에 한 가지만 처리한다.
- **호출 조건 (전부 만족해야 함)**:
  1. 파일 수정 작업이 **전부** 끝났다 (돌고 있는 다른 에이전트가 없다)
  2. qa-reviewer 정적 검증을 이미 통과했다
  3. 지금 실행 중인 unity-operator가 없다
- **금지**: 파일 수정, Play 중 Inspector 값 변경, 확인 대화상자 임의 클릭(반드시 스크린샷 찍고 보고), Unity 외 다른 창 조작
- **종료 시**: Play 정지 확인 + 제어 락 해제

### 3.7 `build-master` — 빌드 / 릴리스

- **한 줄**: 버전 올리고 커밋하고 백업한다.
- **하는 일**: `VERSION` 파일 x.xx.xxx 범프, README 갱신, `/tmp/makegame.git` 워크트리 방식 커밋, `repo.bundle` 백업, 푸시
- **소유 파일**: `VERSION`, `README.md`, git 관련 전부
- **필수 규칙**: **절대 다른 에이전트와 동시에 실행하지 않는다.** git index lock 때문에 반드시 배치 마지막에 단독으로.

## 4. 협업 파이프라인

### 4.1 표준 흐름 (20개 배치 1사이클)

```
[1] 디렉터    : 20개 항목 리스트업 → TaskCreate
      ↓
[2] 기획자    : 각 항목을 스펙으로 변환 (수치·파일·수용 기준)
      ↓
[3] ─┬─ 시스템 ─┐
     ├─  UI    ─┼─ 병렬 실행 (소유 폴더가 안 겹칠 때만)
     └─ 테크아트 ┘
      ↓
[4] QA        : 전체 diff 정적 검증 → 문제 목록 반환
      ↓
[5] 담당자     : QA 지적사항 수정 (원래 짠 사람이)
      ↓
[6] unity-operator : Unity Refresh → Console 확인 → Play 스모크 테스트  ← ★ 단독, 1개만
      ↓  (에러 있으면 [5]로 되돌아감)
[7] 빌드마스터 : 버전 범프 + 커밋 + 번들 백업  ← 단독
      ↓
[8] 디렉터    : 사용자에게 요약 → 즉시 다음 20개 리스트업
```

> [4] QA와 [6] unity-operator는 역할이 다르다. QA는 **코드를 읽어서** 컴파일 에러 후보를 찾고(빠르고 쌈), unity-operator는 **실제로 컴파일을 돌려서** 진짜 결과를 본다(느리고 비쌈). 그래서 QA를 먼저 돌려 뻔한 것들을 걸러낸 뒤, unity-operator를 배치당 1~2회만 쓴다.

### 4.2 병렬로 돌려도 되는 조합

| 조합 | 가능? | 이유 |
|---|---|---|
| 시스템 + UI | ✅ | 폴더가 완전히 분리 |
| 시스템 + 테크아트 | ✅ | `.cs` vs 에셋 |
| UI + 테크아트 | ⚠️ | `Resources/Sprites` 를 둘 다 건드릴 수 있음 → 사전에 파일 목록을 나눠서 지정 |
| 시스템 A + 시스템 B (같은 폴더) | ❌ | 같은 파일 동시 편집 위험 |
| 무엇이든 + 빌드마스터 | ❌ | git lock |
| **무엇이든 + unity-operator** | ❌ | 마우스·키보드가 하나. 파일이 바뀌면 Unity가 재임포트를 시작해 화면 상태가 예측 불가 |
| **unity-operator × 2** | ❌❌ | 절대 금지. 서로의 클릭을 덮어쓰고 씬이 깨진다 |

### 4.3 에이전트 간 요청 규칙

에이전트끼리 직접 대화하지 않는다. **모든 요청은 디렉터를 거친다.**
UI 담당이 시스템 값이 필요하면 → 결과 보고서에 `[요청] SurvivalStats.CurrentThirst 를 public 프로퍼티로 노출 필요` 를 적고 끝낸다. 디렉터가 그걸 읽고 시스템 담당에게 새 작업으로 넘긴다.

## 5. 충돌 방지 규칙 (Unity 특화)

1. **파일 소유권이 곧 락(lock)이다.** 위 표의 소유 폴더 밖은 건드리지 않는다. 필요하면 디렉터에게 요청.
2. **`.meta` 는 짝이다.** 에셋 파일을 추가/이동/삭제할 때 `.meta` 도 같이. 삭제 시 mount 제약으로 지울 수 없으므로 `_to_delete/` 로 이동.
3. **외부 수정 후 Unity에서 Assets > Refresh 필수.** 에이전트가 `.cs` 를 고쳐도 Unity가 재컴파일 안 하면 Play에 반영되지 않는다. 배치 종료 시 디렉터가 사용자에게 항상 안내.
4. **씬 파일(`.unity`)은 원칙적으로 손대지 않는다.** 이 프로젝트는 런타임 코드 생성(`UIBuilder`, `IslandGenerator`) 방식이므로 씬 병합 충돌을 애초에 만들지 않는다.
5. **커밋은 배치당 1회, build-master만.** 중간 커밋 금지.

## 6. 실제 사용 방법

### 6.1 로컬 Claude Code CLI 에서 (`D:\MakeGame` 에서 실행)

`.claude/agents/*.md` 에 정의를 넣어뒀으므로 자동 인식된다.

```
> 모닥불 연료 소모 시스템을 만들어줘
```
→ 디렉터가 알아서 `game-designer` → `systems-engineer` → `qa-reviewer` 순으로 위임.

특정 역할을 지정하고 싶으면:
```
> ui-engineer 로 인벤토리 정렬 기능 추가해줘
> qa-reviewer 로 최근 변경분 전체 검증해줘
```

### 6.2 Cowork(클라우드 세션)에서

클라우드 세션은 `D:\MakeGame\.claude\agents\` 를 직접 읽지 않는다. 대신 이 문서(`Docs/MULTI_AGENT_GUIDE.md`)와 `.claude/agents/*.md` 가 **역할 프롬프트 원본** 역할을 하고, 디렉터가 Agent 도구로 서브에이전트를 띄울 때 해당 역할 정의를 그대로 프롬프트에 실어 보낸다. 사용자는 똑같이 말하면 된다:

```
> 이번 20개는 멀티 에이전트로 진행해줘
```

### 6.3 위임 프롬프트 템플릿

디렉터가 서브에이전트를 부를 때 항상 이 5줄을 채운다:

```
역할: <.claude/agents/<name>.md 의 내용>
목표: <한 문장>
소유 파일: <건드려도 되는 경로 목록>
수용 기준: <무엇이 되면 완료인가>
금지: <절대 건드리면 안 되는 것>
```

## 7. 도입 순서 (한 번에 다 바꾸지 말 것)

| 단계 | 내용 | 효과 |
|---|---|---|
| 1단계 | **QA만 분리**해서 배치 끝에 1회 돌린다 | 가장 싸고 효과 큼. 컴파일 에러·주석 누락을 사람이 Unity 켜기 전에 잡음 |
| 2단계 | **UI ↔ 시스템 병렬화** | 배치 시간이 눈에 띄게 줄어듦 |
| 3단계 | **unity-operator 도입** (단독) | 컴파일 에러를 사람 손 안 거치고 자동으로 확인·수정 루프까지 |
| 4단계 | **기획자 분리** | 수치가 문서에 남아 밸런스 조정이 추적 가능해짐 |
| 5단계 | 테크아트 + 빌드마스터까지 전면 적용 | 완전 팀 구조 |

지금 프로젝트 상태(스크립트 ~50개, 아이콘/텍스처 절차 생성 중)라면 **1~3단계부터** 하는 걸 권장한다.

## 8. 컴퓨터 제어 단일화 규칙 (요약)

이 프로젝트에서 **화면·마우스·키보드를 만질 수 있는 에이전트는 `unity-operator` 하나뿐이다.**

| 항목 | 규칙 |
|---|---|
| 동시 실행 개수 | 항상 **1개**. 예외 없음 |
| 다른 에이전트와 병행 | ❌ 금지. 파일 작업이 전부 끝난 뒤 단독 실행 |
| 다른 에이전트가 Unity 확인이 필요할 때 | 직접 조작하지 말고 `[요청] unity-operator: <확인할 내용>` 으로 보고 |
| 파일 수정 권한 | ❌ 없음. 관찰 결과만 보고, 수정은 원 담당자가 |
| 종료 조건 | Play 정지 + 제어 락 해제 확인 후 종료 |
| 대화상자(Save Scene?, Safe Mode 등) | 임의로 누르지 않고 스크린샷과 함께 디렉터에게 보고 |

Cowork(클라우드) 세션에서는 화면 제어 도구가 메인 세션에만 있으므로, **디렉터가 unity-operator 역할을 직접 겸한다.** 이때도 원칙은 같다 — 그 동안 다른 작업을 병행하지 않는다.

---

## 9. 안 되는 것 / 한계

- Claude Code CLI의 서브에이전트는 화면 제어 도구를 갖지 못하는 경우가 많다. 그런 환경에서는 unity-operator 역할을 **메인 세션(디렉터)이 직접 수행**하고, 나머지 6개만 서브에이전트로 돌린다.
- 에이전트를 많이 띄울수록 토큰이 곱절로 든다. 사소한 수정(오타, 상수 하나)은 디렉터가 그냥 직접 하는 게 싸고 빠르다.
- 병렬 에이전트는 서로의 작업 결과를 실시간으로 못 본다. 서로 의존하는 작업은 반드시 직렬로.
- unity-operator는 화면을 보고 판단하므로 Unity 레이아웃이 바뀌면 흔들린다. Console/Inspector 창 배치를 고정해두는 편이 안정적이다.
