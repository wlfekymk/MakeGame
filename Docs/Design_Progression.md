# Design_Progression.md — 진행 목표 설계

## 0. 이 문서가 푸는 문제

지금 게임은 플레이어를 소형 섬에 떨어뜨린 뒤 **아무것도 말하지 않는다.** 화면에 있는 것은 체력/허기/갈증 바와 "1일차" 라벨뿐이다(`UI/SurvivalHudUI.cs:113`). 목표를 알려주는 UI가 없고, 상호작용 프롬프트조차 없다 — `Systems/InteractionController.cs` 에는 `prompt` 계열 필드가 **하나도 없다**(전수 grep 확인). E키로 뭔가 할 수 있다는 사실을 게임이 알려주는 경로가 존재하지 않는다.

이 문서는 "언제 무엇을 알려줄 것인가"를 5단계 체인으로 고정한다.

## 1. 실측 전제 (근거 표시)

| 항목 | 값 | 근거 |
|---|---|---|
| 1일 = 600초 | 실측 | 씬 `SurvivalClock.secondsPerDay: 600` |
| 배 엔딩 경과일 15일 = **실시간 150분** | 실측 | `EndingChecker.requiredElapsedDays = 15` (코드) × 600초 |
| 배 엔딩 물자: 비상식량 30 · 생수 30 · 연료 1 | 실측 | 씬 `EndingChecker` 직렬화값 |
| 총 섬 9개 (시작 소형 1 + 생성 8) | 실측 | `WorldMapManager.Start()` — `GenerateStartingIsland()` **후에** `initialIslandCount(8)` 루프 |
| 대형 ≥2 · 특대 ≥1 보장 | 실측 | 씬 `IslandGenerator.minimumLargeIslands: 2 / minimumExtraLargeIslands: 1` |
| 시작 섬(id 0)에 **경비행기 잔해 + 배 작업대 둘 다** 존재 | 실측 | `WorldMapManager.GenerateStartingIsland()` 가 `SpawnAircraftWreck` + `SpawnBoatWorkbench` 동시 호출 |
| 특대 섬 진입은 배 1단계 완료 필요 | 실측 | 씬 `IslandTravel.stageRequiredToBypassCurrent: 1` |
| 자원 배율 S/M/L/XL = 1/2/3/4, scatterRadius 80 | 실측 | 씬 `IslandResourceSpawner` (코드 기본값 1/3.24/7.84/16과 **다름**, 씬이 이긴다) |

> ⚠️ 스냅샷 갱신 필요: `HazardSpawner` 배율이 스냅샷에는 1/1.5/2/2.5로 적혀 있으나 **현재 씬 실측은 1/1.75/2.5/3.25** 다(SampleScene.unity 978~981행). 위험 밀도가 문서보다 높다 — 아래 3단계 탐험 난이도 판단은 실측값 기준으로 했다.

## 2. 손도끼 병목 — 재료 병목이 아니라 **인지 병목**이다

브리핑은 "손도끼를 못 만들면 게임이 막힌다"고 전제했다. 레시피를 직접 확인한 결과 **전제가 반쯤 틀렸다.**

- `Recipe_손도끼.asset` 실측: **나뭇가지 1 + 돌조각 2**, `requiredSkillLevel: 1`.
- 씬 `resourceEntries` 실측: 나뭇가지 `baseCount 4 / minimumIslandSize 0 / requiresTool 0`, 돌조각 `baseCount 3 / minimumIslandSize 0 / requiresTool 0`.
- → **시작 소형 섬에서 도구 없이, 스킬 조건 없이, 1~2분 만에 만들 수 있다.** 재료 난이도는 게임 전체에서 가장 낮은 축이다.

진짜 병목은 세 군데다.

1. **손도끼의 설명문이 유일한 실제 용도를 말하지 않는다.**
   `Recipe_손도끼.asset` description: *"나무 채집 속도가 빨라진다."*
   그런데 씬에서 나뭇가지는 `requiresTool: 0` 이다. **손도끼는 나무 채집에 아무 영향도 주지 않는다.** 손도끼가 실제로 여는 유일한 문은 금속조각(`minimumIslandSize: 2` = 대형 이상, `requiresTool: 1`, `requiredTool` = 손도끼, 씬 923~927행)이고, 설명문은 그걸 한 글자도 언급하지 않는다.
   → 플레이어는 손도끼를 "속도 향상용 편의 도구"로 읽고 건너뛴다. 그리고 대형 섬에서 막힌다.

2. **도구 없이 채집을 시도했을 때 아무 피드백이 없다.**
   `ResourceNode.Harvest()`는 도구가 없으면 `return false` 로 조용히 끝난다(`Systems/ResourceNode.cs:94-96`). 소리도, 텍스트도, 실패 표시도 없다. 플레이어는 "버그인가?"라고 판단하고 그 노드를 영원히 포기한다. **이것이 이 게임에서 가장 확실하게 진행을 죽이는 한 줄이다.**

3. **금속조각은 대형 섬 이상에만 있으므로, 손도끼의 필요성은 대형 섬에 도착해야만 드러난다.** 그런데 대형 섬은 왕복 이동 비용이 크다. 도착해서야 "도구가 없다"를 알면 한 번의 왕복이 통째로 낭비된다.

### 설계 결정

- **손도끼 필요성 인지 시점을 "대형 섬 도착 시"에서 "대형 섬 출발 전"으로 앞당긴다.** 방법은 아래 3단계의 준비 체크리스트.
- 재료를 더 쉽게 만들 필요는 전혀 없다(이미 최저 난이도). 대신 **정보를 고친다.**
- [요청] systems-engineer: `ResourceNode.Harvest()` 의 도구 미보유 실패에 실패 신호를 붙일 것 — 최소한 `AudioManager` 실패음 1개 + 화면 중앙 하단 1줄 텍스트("손도끼가 필요합니다"). 이건 밸런스 변경이 아니라 **정보 누락 수정**이다.
- [요청] systems-engineer(또는 데이터 담당): `Recipe_손도끼.asset` / `Item_손도끼.asset` 설명문을 실제 용도로 교체 — "돌을 쪼개 금속 파편을 얻을 수 있다. 큰 섬의 금속 자원 채집에 필요하다." (나는 `.asset` 을 편집하지 않는다.)

## 3. 5단계 목표 체인

각 단계는 **(a) 플레이어가 알아야 할 것 / (b) 전달 수단 / (c) 다음 단계 진입 신호** 로 정의한다.
전달 수단은 우선순위대로 **① 환경 배치 → ② 상시 목표 1줄 → ③ UI 패널** 순으로 고른다. 텍스트 패널은 최후 수단이다.

### 단계 1 — 생존 확보 (0~10분, 1일차)
- **(a)** 갈증이 허기보다 빨리 준다(실측: thirst 0.08/s vs hunger 0.05/s — 갈증이 **1.6배 빠르다**). 코코넛이 즉효 수분이다. 밤에는 위험요소가 보이지 않는다.
- **(b)** 환경 배치로 가르친다 — 상세 설계는 `Design_Onboarding.md`. UI는 **HUD 좌상단 "1일차" 라벨 바로 아래 목표 1줄**만 추가한다. 새 패널을 만들지 않는다(화면 점유 최소).
  - 목표 문구: `물과 음식을 확보하세요`
- **(c) 진입 신호**: 허기·갈증이 둘 다 한 번 이상 70% 아래로 떨어졌다가 회복되면(= 소비 루프를 이해했다) 목표 문구를 단계 2로 교체.

### 단계 2 — 도구 확보 (10~25분, 1~2일차)
- **(a)** 제작은 **V키**다(`CraftingUI.toggleKey = KeyCode.V`). 이 게임에서 가장 발견하기 어려운 키다 — Tab(인벤토리)·M(지도)과 달리 V는 관례가 없다. 그리고 손도끼·창·파이어스타터 3개가 초반 필수 도구다.
- **(b)** 목표 1줄: `제작(V)으로 도구를 만드세요 — 손도끼 · 창`
  - 손도끼: 대형 섬 금속조각의 유일한 열쇠(2장).
  - 창: 생고기 채집의 유일한 열쇠(실측 `필요 도구: 창`). 창이 없으면 단백질 공급원이 생선(도구 불필요, 해안)뿐이다.
  - 파이어스타터(부싯돌 1 + 돌조각 1)는 모닥불 점화용. 부싯돌은 `baseCount 1` 로 초반 자원 중 가장 희소하다 — **이건 목표 문구에 넣지 않는다**(못 찾으면 목표가 거짓말이 된다). 대신 모닥불 키트를 만들었을 때 후속 목표로 등장시킨다.
- **(c) 진입 신호**: 손도끼 보유. 보유 즉시 목표 문구가 단계 3으로 바뀐다 — 이 전환 자체가 "손도끼가 다음 문을 여는 열쇠였다"는 확인이 된다.

### 단계 3 — 탐험 (25~60분, 2~6일차)
- **(a)** 섬은 9개이고 지도는 **M키**다. 대형 섬에는 배 도면(1~2단계)과 금속조각·부력통·엔진부품이 있다. 특대 섬은 지금은 못 간다.
- **(b)**
  - 목표 1줄: `지도(M)를 열어 큰 섬으로 이동하세요`
  - **출발 전 체크리스트**를 미니맵 이동 버튼 옆에 붙인다. 대형/특대 섬을 목적지로 선택했을 때만 표시: `준비: 손도끼 ✓ / 물 ✗`. 손도끼 미보유면 이동 버튼 위에 경고 1줄. **이동을 막지는 않는다** — 막으면 또 다른 소프트락이 되고, 이 프로젝트는 이미 그 사고를 겪었다(`IslandTravel` 주석의 "순환 잠금 버그" 기록).
  - 이것이 2장에서 말한 "인지 시점을 출발 전으로 앞당기는" 실제 수단이다.
- **(c) 진입 신호**: 배 1단계 도면 습득 또는 금속조각 최초 획득.

### 단계 4 — 탈출 준비 (60~150분, 6~15일차)
- **(a)** 여기서 **두 갈래가 처음으로 명시된다.** 지금까지는 하나의 선형 흐름이었다.
- **(b)** 목표 1줄이 2줄이 되는 유일한 지점:
  ```
  탈출 경로 A — 배 제작 (작업대: 시작 섬)   [3단계 중 1단계]
  탈출 경로 B — 경비행기 수리 (잔해: 시작 섬)  [재료 2/15]
  ```
  두 목표물이 **모두 시작 섬에 있다**는 사실(실측)이 여기서 이점이 된다 — "돌아갈 곳이 하나"라는 구조가 자연히 성립한다. 시작 섬을 홈 베이스로 읽게 만드는 것이 이 단계의 진짜 목적이다.
- **(c) 진입 신호**: 어느 한쪽 진행률 100% 도달.

### 단계 5 — 탈출
- `Design_Ending.md` 참조.

## 4. ⚠️ 두 엔딩의 난이도가 균형을 잃었다 (최우선 발견)

실측 재료를 총량으로 환산했다.

**경비행기**: 엔진부품 2 · 금속조각 6 · 연료 3 · 노끈 4 = 실물 15개.
- 노끈 4 = 야자잎 12(`Recipe_노끈`: 야자잎 3 → 노끈 1).
- 엔진부품·금속조각은 대형 섬 `baseCount 2` × 배율 3 = 노드 6개씩.
- **경과 일수 조건 없음.** `EndingChecker.Update()` 는 `aircraftRepair.isRepairComplete` 만 보고 즉시 엔딩을 낸다.

**배**: 3단계 누적 = 대나무 10 · 노끈 14 · 나뭇가지 3 · 금속조각 6 · 부력통 2
- 노끈 14 = **야자잎 42개**.
- 도면 3장(대형 섬 2회 + 특대 섬 1회 방문 강제).
- **추가로 비상식량 30 · 생수 30 · 연료 1.**
- 비상식량은 씬 `baseCount 1` — 소형 섬 1노드, 대형 섬 3노드. 30개는 리스폰(`respawnSeconds` 기본 60초) 대기를 반복해야 하는 수량이다.
- **그리고 15일 = 실시간 150분 강제 대기.**

→ **경비행기 엔딩이 배 엔딩보다 재료로 약 4배, 시간으로 최소 3~5배 싸다.** 플레이어가 두 경로를 다 알면 배 엔딩은 아무도 선택하지 않는다. 배 엔딩에 투입된 제작·도면·물자 시스템 전체가 죽은 콘텐츠가 된다.

### 판단
난이도를 맞추려고 **경비행기를 어렵게 만들지 않는다.** 대신 **의미를 다르게 준다.**

- 경비행기 = **탈출 (Escape)**. 살아서 나갔다. 준비 없이, 아는 것 없이, 급하게.
- 배 = **귀환 (Return)**. 15일을 버티고 물자를 갖춰 스스로의 힘으로 돌아왔다.

이 차이를 **엔딩 연출과 요약 통계로만** 표현한다(`Design_Ending.md` 2장). 조건은 손대지 않는다 — 조건 변경은 씬 값 수정이고, 지금 4명이 병렬 편집 중인 상황에서 밸런스 충돌 위험이 크다.
단, 단계 4 목표 표기에서 **경비행기를 먼저 쓰지 않는다.** 배를 A로, 경비행기를 B로 표기해 기본 안내 경로를 배로 둔다.

## 5. 150분을 무엇으로 채울 것인가

15일 조건은 실질적으로 **"배 재료를 다 모은 뒤 남는 빈 시간"** 을 만든다. 실제 소요를 추정하면:

| 활동 | 추정 소요 | 근거 |
|---|---|---|
| 도구 확보 + 첫 탐험 | ~30분 | 추정 |
| 도면 3장 + 배 재료 전량 | ~50분 | 추정 (대형 2회·특대 1회 왕복 포함) |
| **비상식량 30 + 생수 30** | **~60분+** | 반쯤 실측 — `baseCount 1`, 리스폰 60초 |
| 합계 | ~140분 | |

→ **결론: 150분은 비어 있지 않다. 오히려 빠듯하다.** 다만 마지막 60분이 **"노드 앞에서 리스폰을 기다리는 시간"** 이라는 게 문제다. 이건 콘텐츠가 아니라 대기다.

### 제안 (우선순위 순)

1. **생수 30은 물증류기로 해결되게 한다** — 이미 `WaterStill` 프리팹 `waterPerSecond: 0.3 / maxStorage: 20`(스냅샷 2장 (1)). 0.3/s면 20 채우는 데 67초. 30개는 증류기 2대로 충분히 커버된다. → 단계 4 목표에 `물 증류기를 설치하면 식수가 자동으로 모입니다` 를 후속 힌트로 노출. **대기가 "설치해두고 다른 일 하기"로 바뀐다.** 코드 변경 없이 정보만으로 해결되는 가장 싼 개선이다.
2. **비상식량 30이 진짜 대기 구간이다.** 씬 값 변경 없이 채우려면, 이 60분에 **반복해도 되는 활동**을 배치해야 한다. 현재 게임에 이미 있는 것 중 반복 가치가 있는 것: 사냥(창, 성공률 0.7, 리스폰 90초) · 낚시(도구 불필요, 0.6, 60초) · 조리 · 쉼터/모닥불 설치. → 목표 1줄을 이 시기에 **"밤을 안전하게 보낼 거점을 만드세요"** 로 전환해, 대기 시간을 거점 구축 시간으로 재프레이밍한다.
3. **[요청] balance 담당**: 비상식량 30이 정말 의도인지 재확인. `baseCount 1` 자원을 30개 요구하는 것은 다른 어떤 요구치보다 한 자릿수 크다. 만약 "30일치 식량"이라는 서사 의미가 목적이라면, **비상식량 대신 구운고기/구운생선을 포함한 보존식 합산**으로 바꾸는 편이 서사도 살고 대기도 사라진다. 이건 내가 판단할 수 없고 코드/씬 변경이 필요하다.
