# Design_Ending.md — 엔딩 연출 설계

## 0. 지금 무슨 일이 일어나는가

`EndingChecker.TriggerEnding()` 실측 동작 순서:
1. `endingTriggered = true`, 메시지 문자열 1개 저장
2. `GameManager.CompleteEnding()`
3. `showEndingUI = true` → `EndingUI` 가 다음 프레임에 패널을 연다
4. `playerController.enabled = false`, `interactionController.enabled = false`
5. **`Time.timeScale = 0f`**
6. `AudioManager.PlayStageComplete()`

화면에 뜨는 것은 문장 **한 줄**이다.
- 배: `"배를 타고 섬을 탈출했습니다!"`
- 비행기: `"경비행기를 수리해 하늘로 섬을 탈출했습니다!"`

150분(배 엔딩 기준)을 투자한 플레이어가 받는 보상이 이것이다. **감정적 마무리가 없다는 진단은 정확하다.** 게다가 두 문장은 서로 다른 경로였다는 사실 외에 아무 차이도 표현하지 않는다.

## 1. 구현 제약 — 이 안에서만 설계한다

`ArtDirection.md` 0장 확인: **3D 모델 0개, 전부 프리미티브.** 그리고 이 코드베이스에는 추가 제약이 두 개 더 있다.

### 제약 A — `Time.timeScale = 0` 이 즉시 걸린다
`TriggerEnding` 5번째 줄에서 시간이 멈춘다. **`Time.deltaTime` 을 쓰는 어떤 연출도 그 뒤로는 절대 진행되지 않는다.** 코루틴의 `WaitForSeconds` 도 멈춘다.
→ 모든 연출은 **`Time.unscaledDeltaTime` / `WaitForSecondsRealtime`** 으로 작성해야 한다. 코드베이스에 이미 근거 주석이 있다 — `EndingUI.OnContinueClicked` 주석의 "timeScale 0에서도 UGUI 입력은 정상 동작한다". 같은 원리로 UI 애니메이션은 unscaled면 돈다.
→ **이 한 가지를 놓치면 연출이 통째로 정지 화면이 된다.** 가장 먼저 전달해야 할 사실이다.

### 제약 B — 컷신 불가
카메라 이동으로 배가 떠나는 장면을 만들려면 배 오브젝트, 항해 애니메이션, 궤도 카메라가 필요하다. 셋 다 없다.
→ **컷신을 시도하지 않는다.** 대신 **정지 화면의 순차 구성(sequential reveal)** 으로 시간감을 만든다. 이건 UGUI 텍스트/이미지 알파 보간만으로 구현되고, 이 프로젝트가 확실히 할 수 있는 일이다.

### 쓸 수 있는 것 (전부 이미 코드에 존재)
- `UIBuilder.CreateText` / `CreateButton` / 패널 알파 규칙(`ArtDirection.md` 4.3)
- `EndingUI` 의 배경 로직 — 이미 `title_background` 이미지 + 금색 오버레이, 없으면 단색 폴백을 구현하고 있다(`EndingUI.BuildUI` 주석)
- `AudioManager.PlayStageComplete` (승리 팡파르)
- `DayNightCycle` 의 색상 값 — 아래 3장에서 배경색 근거로 사용
- 핵심 팔레트 8색(`ArtDirection.md` 1.1)

## 2. 두 엔딩의 의미를 갈라놓는다

`Design_Progression.md` 4장의 결론: **경비행기가 배보다 재료 4배·시간 3~5배 싸다.** 조건은 손대지 않고 **연출로만** 차별화한다.

| | 경비행기 | 배 |
|---|---|---|
| 이름 | **탈출** | **귀환** |
| 톤 | 급박, 미완, 안도 | 완결, 준비됨, 성취 |
| 배경색 | `Deep Ocean #1A598C` → 밝게 (하늘로) | `duskDawnColor #FF9959` (노을, 수평선) |
| 팡파르 | 짧게 1회 | 통계 공개와 함께 단계적으로 |
| 마지막 문장 | 물음을 남긴다 | 답을 준다 |
| 통계 공개 | **일부만** (3항목) | **전부** (6항목) |

**통계 공개량의 차이가 이 설계의 핵심 장치다.**
경비행기 엔딩은 "이 섬에 대해 아직 모르는 게 많다"를 통계 칸이 비어 있는 것으로 보여준다. 플레이어가 스스로 "다른 엔딩이 있구나"를 눈으로 확인하게 만든다. 텍스트로 "다른 엔딩도 있습니다"라고 말하는 것보다 훨씬 강하고, 구현 비용은 같다.

배 엔딩은 첫 엔딩을 이미 본 뒤에도 계속 플레이 가능하다(`DismissEndingUI` 주석: "첫 엔딩 이후에도 자유 플레이 허용"). 즉 **경비행기 → 배 순서로 두 번 보는 것이 이미 설계상 가능하다.** 이 구조를 통계 비대칭이 지지한다.

## 3. 연출 시퀀스

두 엔딩 공통 골격. 전부 `unscaledDeltaTime` 기반. 총 길이 약 7초 + 대기.

### 페이즈 0 — 정지 (0.0s)
`TriggerEnding` 이 현재 하는 일 그대로. 단 **`PlayStageComplete` 를 여기서 울리지 않는다** — 페이즈 2로 옮긴다. 지금은 화면에 아무것도 뜨기 전에 팡파르가 먼저 울려서 소리와 그림이 어긋난다.

### 페이즈 1 — 암전 (0.0s → 1.0s)
검정 오버레이 알파 0 → 1. 게임 화면을 완전히 덮는다.
- **왜**: 프리미티브 월드를 그대로 배경에 남겨두면 "게임이 멈춘 화면"으로 읽힌다. 지워야 "장면이 바뀌었다"가 된다. 컷신 없이 장면 전환을 만드는 유일한 수단이다.

### 페이즈 2 — 배경 + 제목 (1.0s → 2.5s)
검정 → 엔딩별 배경색으로 크로스페이드. 제목 텍스트 페이드 인. **여기서 `PlayStageComplete`.**
- 경비행기: 배경 `#1A598C` → `#73A6D9`(daySkyTint, 실측) 그라데이션. 제목 **`탈출`**, 폰트 48.
- 배: 배경 `#FF9959`(duskDawnColor, 실측) 단색. 제목 **`귀환`**, 폰트 48.
- 색은 전부 `DayNightCycle`/팔레트에 이미 있는 값이다. 새 색을 만들지 않는다(`ArtDirection.md` 1장 원칙).

### 페이즈 3 — 통계 순차 공개 (2.5s → 6.0s)
한 줄씩 0.4초 간격으로 페이드 인. **이 순차성이 이 연출의 유일한 "움직임"이다.** 한 번에 다 띄우면 정지 이미지가 되고, 순서대로 뜨면 리듬이 생긴다. 비용은 알파 보간 6개.

| # | 항목 | 데이터 출처 | 배 | 비행기 |
|---|---|---|---|---|
| 1 | 생존 일수 | `SurvivalClock.ElapsedDays + 1` (`SurvivalHudUI:259` 와 동일 표기) | ✓ | ✓ |
| 2 | 방문한 섬 | `WorldMapManager.islands` 중 `isDiscovered` 개수 / 총 9개 | ✓ | ✓ |
| 3 | 제작한 물건 종류 | 신규 카운터 필요 (4장) | ✓ | ✓ |
| 4 | 배 제작 진행 | `BoatConstructionSystem.GetOverallProgress()` | ✓ | ✗ (미표시) |
| 5 | 최대 채집 스킬 레벨 | `PlayerSkills.GetLevel(Harvesting)` | ✓ | ✗ |
| 6 | 겪은 위기 횟수 | 신규 카운터 필요 (4장) | ✓ | ✗ |

**비행기 엔딩에서 4~6번 자리는 빈칸으로 남기지 않는다** — 회색 `#CCCCCC` 알파 0.4 로 `— — —` 를 표시한다. 빈칸은 버그로 보이지만, 흐린 대시는 "여기 뭔가 있는데 네가 채우지 못했다"로 읽힌다.

### 페이즈 4 — 마지막 문장 + 계속하기 (6.0s → 7.0s)
- 경비행기: `섬은 아직 그 자리에 있다.`
- 배: `당신은 준비된 채로 떠났다.`

두 문장 모두 "탈출했습니다!" 같은 느낌표 보고문이 아니다. **느낌표를 지우는 것 자체가 이 문서의 결정이다.** 150분짜리 생존 게임의 마지막 문장이 감탄사면 무게가 안 맞는다.

그 아래 기존 계속하기 버튼(`EndingUI.OnContinueClicked` → `DismissEndingUI`). 문구는 `계속하기 (Space)` 로 유지 — 씬 실측 `continueKey: 32`(Space)와 일치한다.

### 스킵
페이즈 1~3 동안 아무 키나 누르면 페이즈 4로 즉시 점프. **두 번째 플레이에서 7초를 강제로 앉혀두면 연출이 벌칙이 된다.**

## 4. 신규로 필요한 데이터 2개

통계 3·6번은 현재 어디에도 집계되지 않는다.

- **제작한 물건 종류 수**: `CraftingSystem.TryCraft` 성공 시 `recipe` 를 `HashSet` 에 담기만 하면 된다. `TryCraft` 는 이미 성공 분기가 명확히 분리돼 있어(`AudioManager.PlayCraftSuccess` 바로 옆) 삽입 지점이 한 줄이다.
- **겪은 위기 횟수**: `SurvivalStats.lastDamageCause` 가 이미 사인 7종을 추적한다(`GameOverController.GetDeathMessage` 실측). 원인이 `None`→유효값으로 바뀌는 전환을 세면 된다. 새 상태 없이 카운터 int 1개.

둘 다 저비용이고, 세이브에 넣지 않아도 된다(엔딩은 한 세션 안에서 완결되므로). **[요청] systems-engineer.**

## 5. 실패 엔딩 (사망)

`GameOverController` + `UI/GameOverUI` 가 이미 동작한다. 실측 현황:
- `GetDeathMessage()` 가 사인별 문구 **7종**을 반환한다 — 굶주림/일사병/중독/출혈/익사/포식자/상어. **이 자산이 지금 충분히 안 쓰이고 있다.**
- `GameOverUI` 화면: 제목 `"게임 오버"` 폰트 48 **빨강**, 메시지 폰트 20, 재시작 버튼.
- 즉시 `Time.timeScale = 0`, `PlayDamage()` 재생.

### 문제 3가지와 결정

**(1) 제목이 빨강 48pt다.** `UIBuilder.CreateText(panel, "Title", "게임 오버", 48, Color.red, ...)` — `Color.red`(`#FF0000`)는 팔레트에 없는 순색이다. `ArtDirection.md` 1.3이 정적 위험 표시를 `Danger Red #CC3333` 로 통일했는데 여기만 예외로 남아 있다.
→ **결정**: `#CC3333` 로 교체. 그리고 제목 문구를 `게임 오버` → **`이곳에서 끝났다`** 로 바꾼다. "게임 오버"는 시스템 언어이고, 이 게임의 다른 모든 문구(사인 7종)는 서사 언어다. 톤이 섞여 있다.
- [요청] ui-engineer: `GameOverUI` 제목 색 `Color.red` → `#CC3333`, 문구 교체.

**(2) 사망 엔딩에 성취 통계가 없다.** 승리 엔딩과 대칭이 무너진다. 죽었어도 8일을 버텼고 섬 5개를 봤다면 그건 사라져야 할 정보가 아니다.
→ **결정**: 승리 엔딩과 **동일한 통계 3항목**(생존 일수 / 방문한 섬 / 제작한 물건)을 사망 화면에도 표시한다. 순차 공개는 하지 않는다 — 사망은 축하가 아니므로 리듬을 주지 않고 한 번에 띄운다. **연출 차이가 곧 감정 차이다.**

**(3) 사망 화면이 다음 시도를 돕지 않는다.**
→ **결정**: 사인에 대응하는 **회피 힌트 1줄**을 사망 문구 아래 폰트 12로 붙인다. 사인 7종에 1:1로 매핑되므로 문자열 7개 추가로 끝난다.

| 사인 | 힌트 |
|---|---|
| Starvation | `코코넛과 생선은 도구 없이도 구할 수 있다.` |
| Sunstroke | `쉼터의 그늘에서는 체온이 회복된다.` |
| Poison | `해독제는 코코넛 1 + 천조각 1로 만든다.` (실측 `Recipe_해독제`) |
| Bleeding | `붕대는 천조각 2로 만든다.` (실측 `Recipe_붕대`) |
| Drowning | `깊은 물에서는 산소가 빠르게 준다.` |
| Predator | `창을 들면 맞설 수 있다. 밤에는 피하는 편이 낫다.` |
| SharkAttack | `지느러미가 보이면 이미 가까이 있다.` |
| (기타/None) | `허기와 갈증을 먼저 관리하라.` |

레시피 수치는 전부 실측 에셋에서 가져왔다 — **힌트가 틀리면 힌트가 아니라 함정이 된다.**

## 6. 우선순위

`ArtDirection.md` 5장과 같은 기준(효과 × 빈도 ÷ 비용).

| 순위 | 항목 | 근거 |
|---|---|---|
| 1 | `unscaledDeltaTime` 전제 공유 (1장 제약 A) | **비용 0.** 모르고 만들면 연출 전체가 무효가 된다 |
| 2 | 사망 화면 회피 힌트 8줄 (5-3) | 문자열만 추가. 사망은 승리보다 훨씬 자주 보는 화면이다 |
| 3 | 통계 카운터 2개 (4장) | 두 엔딩 + 사망 화면 셋 다에 쓰인다 |
| 4 | 통계 순차 공개 (페이즈 3) | 연출의 핵심. 알파 보간만으로 구현 |
| 5 | 암전 → 배경 전환 (페이즈 1~2) | 컷신 없이 장면 전환을 만드는 유일한 수단 |
| 6 | 제목/문장 교체 (2·3·5장) | 저비용, 톤 정리 |
| 7 | 배경색 엔딩별 분기 | 위가 다 되면 자연히 따라온다 |

## 7. 확인 필요

- [확인요청] 디렉터: 엔딩 제목을 `탈출`/`귀환` 두 단어로 가는 방향. 기존 문장("배를 타고 섬을 탈출했습니다!")은 `EndingChecker.TriggerEnding` 호출부의 인자라 **`.cs` 수정이 필요하다** — 나는 편집하지 않았다.
- [확인요청] systems-engineer: `EndingChecker.Update()` 는 배 엔딩을 먼저 검사하고 `return` 한다. 같은 프레임에 두 조건이 모두 성립하면 **배가 이긴다.** 의도인지 확인 필요 — 배가 더 어려운 경로이므로 결과적으로는 타당해 보이나, 명시된 판단이 아니라 코드 순서의 부산물이다.
- [확인요청] systems-engineer: 씬의 `EndingChecker` 에 `survivalClock` 이 실제로 연결됐는지. 코드에는 필드가 **이미 존재**하고(`EndingChecker.cs:43`) 미연결 시 조건을 통과시키는 안전 처리가 있다. 즉 **미연결이면 15일 조건이 조용히 사라져 배 엔딩이 비행기만큼 빨라진다** — 이 문서 2장의 차별화 전제가 통째로 무너진다. `Balance_SceneSnapshot.md` 2장 (2)는 "필드 자체가 없다"고 기록돼 있어 스냅샷 이후 코드가 갱신된 상태다. 씬 연결 여부만 확인하면 된다.
